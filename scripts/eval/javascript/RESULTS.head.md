# vibepiler vs the JS/TS toolchain

vibepiler 0.4.5 (commit d9ca2bb) against knip, ts-prune, ts-unused-exports, depcheck, jscpd, madge and ESLint
(`complexity`, `sonarjs/cognitive-complexity`, `no-empty`, `no-unused-vars`) on six pinned JS/TS repos.
Raw numbers are in `results.json`. Every table below is regenerated by `sh scripts/eval/javascript/run.sh` (from the repo root; clones, tools and raw outputs go to `.eval/javascript/`, or `$VIBEPILER_EVAL_WORK`), and
`sh scripts/eval/javascript/run.sh --skip-setup` reruns everything after setup.

**Machine:** Apple M3 Max, 14 cores, 36 GB, macOS 15.8.1, Node 25.1.0, Python 3.12.2. Two other evaluation
agents shared the machine during the runs, so the timings are noisy. The OS file cache was not flushed (that needs
root), so "cold" here only means the harness's first run.
**Tool versions:** knip 6.44.2, ts-prune 0.10.3, ts-unused-exports 11.0.1, depcheck 1.4.7, jscpd 5.4.3 (the new
native rewrite), madge 8.0.0, eslint 10.14.0, eslint-plugin-sonarjs 4.2.2, @typescript-eslint/parser 8.72.1,
typescript 6.0.3, pnpm 12.18.0. They are installed in `tools/`.

## Corpus

| repo | pinned | kind | why |
|---|---|---|---|
| zustand | v5.1.0 `9fed2eb` | small library, TS | well known; package.json `exports` subpaths are a hard entry-point test |
| release-it | 21.1.2 `10bce41` | mid CLI, plain JS (ESM) | written by knip's author and ships a `knip.json`, so knip plays at home |
| taxonomy | main `298a885` | mid Next.js 13 app, TS | app router plus pages, contentlayer, middleware: framework entry points |
| excalidraw | v0.18.1 `a2ec288` | large monorepo, TS (yarn workspaces) | 535 files, 136k lines |
| scuttlepay | main `4af6d02` | vibe-coded Next.js + pnpm workspace, TS | 71 of its last 100 commits carry a Claude co-author trailer; ships CLAUDE.md; built for a Claude Code hackathon |
| tower-of-time | main `a2497fb` | vibe-coded Phaser game, TS | its GitHub description says "Vibe coded Tower Defense"; ships PROMPTS.md (the prompts used) and .cursorrules |

The full SHAs are in `scripts/eval/javascript/pins.txt`. "Vibe-coded" was judged from the repo's own evidence: commit trailers, a
CLAUDE.md or PROMPTS.md, and a self-description. It was not judged from the code's style.

**Setup and safety notes.** Dependencies were installed with `pnpm install --ignore-scripts` (excalidraw:
`npm install --ignore-scripts --legacy-peer-deps`; release-it also needed `engine-strict=false` for Node 25). The
installers rewrote lockfiles. No repo script, hook or test was run. **One deviation:** knip resolves entry points by
*loading the repo's config files* (next.config.js, vite/drizzle/eslint configs), which runs repo code. I noticed this
on scuttlepay, where `next.config.js` imports an env validator that threw. By then knip had already run 4–5 times
per repo. I read the configs of the two least-trusted repos (scuttlepay: next/drizzle/eslint/prettier/postcss
configs; tower-of-time: the vite configs) and they are benign. From then on knip and depcheck ran inside a macOS
`sandbox-exec` profile that denies the network (`scripts/eval/javascript/nonet.sb`), and all knip and depcheck numbers here come from
those sandboxed runs. On scuttlepay knip ran with `SKIP_ENV_VALIDATION=1` and a stub `DATABASE_URL`, as knip's
known-issues page advises. Without them knip exits 2 with partial results. vibepiler, madge, jscpd, ts-prune and
ts-unused-exports parse the code without running it. ESLint ran with `--no-config-lookup` and my own config, so it
never loads a repo config.

**Normalization.** Every finding becomes (file relative to the repo, symbol or line, kind).
- *Files:* vibepiler `unreachable-module` vs knip `files`.
- *Exports:* vibepiler `unused-export` vs knip `exports+types+nsExports+nsTypes` vs ts-prune vs ts-unused-exports,
  keyed (file, name). In the "broad" set, vibepiler also counts `dead-symbol` and `unreachable-symbol` findings on
  exported top-level symbols. The "files neither flags" row drops exports inside files either tool calls unused,
  because knip does not list exports of unused files.
- *Dependencies:* (manifest, package), restricted to the manifests knip analyses (root and declared workspaces).
  Undeclared dependencies are keyed by package name.
- *Duplicates:* the unit is a vibepiler function node. A function counts as found by jscpd when a clone fragment
  covers at least 50% of its lines.
- *Cycles:* the set of modules that sit in any cycle. madge `--circular` lists only some elementary cycles, so I
  also took the SCCs of madge's full dependency graph.
- *Complexity:* functions matched on (file, start line), with ESLint and SonarJS at threshold 0 so every function
  reports its number.
- *Swallowed exceptions:* (file, line ±3).

## Findings

### 1. Speed: vibepiler alone is about as fast as knip alone on small repos, about 5× slower on the large one, and 3–11× faster than the whole toolchain
- **Small and mid repos (8–15k lines):** vibepiler -O2 takes **0.55–0.91 s**, knip **0.36–1.01 s**. knip is
  faster on release-it, scuttlepay and tower-of-time; vibepiler is faster on taxonomy and about equal on zustand.
- **excalidraw (136k lines):** vibepiler takes **5.47 s** (25 kLOC/s), knip **1.17 s** (117 kLOC/s).
  `vibepiler -v` breaks the 5.5 s down into parse 0.9 s, link 0.8 s, passes 2.2 s (complexity 0.94 s, liveness
  0.56 s) and writing 28 MB of reports (ir.json 16 MB, report.html 12 MB) about 0.9 s. The remainder is interpreter
  start-up and graph building.
- **Whole toolchain:** the seven tools in sequence take **2.4–19.9 s**, **3.3–10.8×** vibepiler -O2. jscpd 5 is
  native and the fastest tool here (0.07–0.15 s). ESLint, depcheck and ts-prune cost the most.
- **-O1 vs -O2:** duplicate detection is cheap. -O2 adds 0–0.24 s.
- **Peak RSS:** vibepiler uses 83–106 MB on the small repos and 455 MB on excalidraw. That is below every Node tool
  except jscpd; ESLint peaked at 1.19 GB and ts-prune at 1.04 GB on excalidraw.

### 2. Determinism: perfect
All 6 repos × {-O1, -O2} × 4 runs (1 cold + 3 warm) produced byte-identical diagnostics: same sorted set, same order,
and the same node/edge graph.

### 4. Precision where the tools disagree (hand-verified by reading the code)
| sample | TP | FP | unclear | precision |
|---|---|---|---|---|
| vibepiler-only dead code (vs knip), 15 of 173 | 1 | 14 | 0 | **7%** |
| knip-only dead code, 15 of 175 | 12 | 3 | 0 | **80%** |
| vibepiler-only dependency findings (vs knip ∪ depcheck), 10 of 14 | 0 | 9 | 1 | **0%** |
| knip/depcheck-only dependency findings, 10 of 92 | 3 | 6 | 1 | 30% (most FPs are depcheck's) |
| vibepiler-only unused imports (vs ESLint), 10 of 151 | 1 | 9 | 0 | 10% |

When vibepiler and knip disagree about dead code, knip is usually right. Most of vibepiler's extra dead-code findings
come from four resolution gaps, listed in §5. knip's own false positives are example apps that are not workspaces and
a library's public API re-exported from `src/middleware.ts`, which knip cannot map from package.json `exports` (dist)
back to src. knip catches three things vibepiler misses: barrel re-exports nobody uses, exports used only inside
their own file, and never-imported names in a trailing `export { … }` list.

### 5. Suspected vibepiler bugs (each one verified by reading the code)
1. **Star and named re-exports from an entry module do not keep their targets alive.** In zustand, `src/index.ts:1-2`
   does `export * from './vanilla.ts'` / `'./react.ts'`, yet `create` (`src/react.ts:63`) is reported as an unused
   export and `createStore` (`src/vanilla.ts:99`) as unreachable. Those are the library's main API. In the same way,
   `src/middleware.ts:8` does `export { combine } from`, yet `combine` (`src/middleware/combine.ts:5`) is reported.
2. **tsconfig `paths` aliases and self-imports are not resolved.** zustand tests import
   `zustand/middleware/immer`, which leads to `unreachable-module src/middleware/immer.ts` plus
   `undeclared-dependency zustand`. excalidraw's `@excalidraw/math|utils|excalidraw` aliases (tsconfig.json:21-28)
   lead to `getPolygonShape` (`packages/utils/geometry/shape.ts:113`) as dead, `rangeIntersection`
   (`packages/math/range.ts:56`) as test-only, and import edges missing from the cycle graph.
3. **pnpm/yarn workspace package imports are not mapped to the package's source.** Its `main` points at dist. In
   scuttlepay, `ScuttlePayError`, `isScuttlePayError` and `ProductSearchResult` (`packages/shared/src/*.ts`) are
   reported dead even though packages/mcp and the app import them from `@scuttlepay/shared`.
4. **package.json `bin` and `scripts`, and config references, are not entry points.** Examples:
   `release-it/bin/release-it.js` (the CLI itself), and 12 of the 14 files vibepiler flags under excalidraw's
   `scripts/`, which package.json scripts or CI workflows run (or which those files require). The other two,
   `buildDocs.js` and `buildWasm.js`, really are unreferenced, and knip agrees. Also `setupTests.ts`
   (`vitest.config.mts:41` `setupFiles`).
5. **TypeScript declaration merging breaks linking.** tower-of-time `src/prefabs/Player.ts:10/14` has
   `export default interface Player` + `export default class Player`. The class is reported as an unused export
   although `Level.ts` does `new Player(...)`, and that cascades to `PlayerMenu` and `MenuItemData`.
6. **unused-import ignores many uses.** It misses type positions (generic constraints `<P extends A | B>`,
   `interface X extends Y`, `satisfies T`, types inside a constraint) and even a value used as a default parameter
   (`threshold = PRECISION`, excalidraw `packages/math/polygon.ts:4/46`). It also reads `export { a as b } from`
   as an unused import (zustand `src/middleware.ts:17`). Nine of the ten sampled cases are false positives.
7. **A trailing `export { X }` list counts as a use of X** (a `references` edge with context `export`), so exports
   that nothing imports are never reported when declared that way. Example: scuttlepay
   `src/components/ui/dialog.tsx:147` `DialogFooter`, and the same shadcn pattern in taxonomy. This is a false
   negative.
8. **swallowed-exception misses `catch {}` inside an arrow in a JSX attribute**: excalidraw
   `excalidraw-app/CustomStats.tsx:63`.
9. **The dependency pass reads only imports.** It ignores package.json fields (`"prettier": "@excalidraw/prettier-config"`),
   CLIs run by scripts (`json`, `installed-check`, `phaser-asset-pack-hashing`), config strings (vite
   `minify: 'terser'`) and peer dependencies (`redux` for @redux-devtools/extension, `nodemailer` for next-auth,
   `prop-types`, `react` in a Next app). It does this by design (no node_modules), but it produced 9 of the 10
   sampled vibepiler-only dependency FPs. Undeclared-dependency also flags root-hoisted devDeps in workspaces
   (`vitest` in packages/excalidraw), Vite virtual modules (`virtual:pwa-register`) and Docusaurus aliases
   (`@site/*`, `@theme/*`).
10. **Complexity definition.** Nested closures count toward the enclosing function: zustand `devtoolsImpl` scores 56
    against ESLint's 2, and excalidraw `App.onPointerUpFromPointerDownHandler` 128 against 1, because the real logic
    lives in the returned closure. vibepiler then flags 190 functions where ESLint flags 74. This may be intended,
    but it does not match SonarJS's per-function scores, and the README says vibepiler follows the Sonar paper.

### 6. Novelty: what no compared tool reports
770 findings (of 2,528) fall in 16 kinds no compared tool covers: per repo zustand 53, release-it 39, taxonomy 141,
excalidraw 458, scuttlepay 58, tower-of-time 21. The largest kinds are `unreachable-symbol` 382 (transitively dead),
`thin-wrapper` 109, `single-use-helper` 62, `test-only` 58, `bloated-module` 47, `unimplemented-interface` 20,
`god-module` 18, `pass-through-wrapper` 16, `indirection-chain` 15, `log-and-reraise` 14 and `tiny-module` 14. Dead
**class methods** (`dead-symbol` on methods, which knip does not report by default) were 6/6 TP in a tower-of-time
spot check (`ConfigSystem.resetToDefaults`, `WaveSystem.skipToNextWave`, `GoalHPSystem.heal`, ...): unused methods
of the kind a vibe-coded repo accumulates. Other kinds have standard ESLint rules that were not run (`long-function`,
`deep-nesting`, `too-many-params`, `dead-store`, `stub-function`, `redundant-try`) and are not counted as novel.
Caveat: the novel kinds inherit the resolution bugs above. `unreachable-symbol` contains zustand's whole `createStore`
chain, and one `test-only` spot check (`rangeIntersection`) was an alias false positive while another (`touch` in
release-it) was right. The wrapper findings I read were structurally correct but often intentional, such as
deferred thunks passed to a retry and a Next.js server-action boundary.

### Bottom line
vibepiler is deterministic and light on memory, and it runs the whole battery 3–11× faster than the toolchain it
replaces. Its cycle detection matches madge's real SCCs. On undeclared dependencies it matches depcheck, and it
finds most of jscpd's Type-2 duplicate functions. On the dead-code and dependency passes, the JS/TS module resolution
is the weak point: tsconfig paths, workspace packages, star re-exports, package.json bin/scripts, declaration
merging and peer dependencies. Until those are fixed, a vibepiler-only dead-code finding on a JS/TS repo is more
likely wrong than right.
